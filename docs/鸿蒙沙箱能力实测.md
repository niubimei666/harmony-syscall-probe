# 鸿蒙沙箱能力实测：为什么 DSH 本机引擎跑不起来

> 本文记录 2026-11-04 至 11-06 的一组实测，回答一个具体问题：
> **DeepSeek Harness（DSH）的本机引擎能不能在鸿蒙设备上跑？**
>
> 结论按环境分三层，各不相同。所有数据都来自可复现的探针测量，命令与源码随文附上。

---

## 摘要

| 环境 | seccomp | socket | ptrace | clone3 | 本机引擎 |
|---|---|---|---|---|---|
| `hdc shell`（`u:r:sh:s0`） | **0 filters** | — | — | — | 不能执行二进制 |
| **纯血鸿蒙原生应用**（`u:r:debug_hap:s0`） | **2 filters** | ✅ | ✅ | 💀 | 卡在 glibc + W^X |
| 安卓兼容容器（卓易通 / Anco） | 严格白名单 | ❌ | ❌ | ❌ | **物理不可行** |

四句话版本：

1. **鸿蒙系统不拦 `socket` / `ptrace` / `clone`** —— 之前「鸿蒙跑不了本机引擎」的说法，是把容器的限制误当成了系统的限制。
2. **真正被拦的是 Linux 5.x 之后的新 syscall**（`clone3` / `rseq` / `openat2` / `io_uring` / `get_robust_list`），所以现代 glibc（2.34+）起不来。
3. **应用沙箱有 W^X + 代码签名约束**：`execve` 和 `mmap(PROT_EXEC)` 对运行时写入的文件都被 EACCES 拒，但 **HAP `libs/` 目录里的 `.so` 可以 dlopen**（已实测）。
4. **所以原生鸿蒙要把 Node 编译进 HAP 的 `libs/`**，不能「在应用里启动一个 node 进程」，也不能运行时加载自己写的 `.so`。这条路已实测可行。

---

## 一、背景

有一个把 DSH 装进手机的开源客户端，用 PRoot + rootfs 在 Android 上跑完整 Linux 环境。用户在鸿蒙设备上通过「卓易通」这个 Android 兼容容器安装它，引擎 100% 启动失败：

```
sh: 0: getcwd() failed: Function not implemented
/bin/sh: 1: exec: /usr/local/bin/dsh: Bad address
```

社区已有两份重要材料：

- **逐 syscall 静态探针**：用 461 个微型 ELF 测出卓易通容器是严格 syscall 白名单，并验证了 glibc 补丁方案（但补丁后引擎仍然起不来）
- **原生鸿蒙移植**：有第三方贡献者完成了移植并提供了侧载安装包

本文补的是**第三块拼图**：纯血鸿蒙原生应用沙箱到底允许什么。

## 二、测量方法

### 2.1 为什么不能直接在 shell 里测

两个坑必须先说清楚，否则测出来的数据是错的：

**坑 1：`hdc shell` 的上下文 ≠ 应用沙箱。**

```
$ hdc shell cat /proc/self/status
Seccomp:         0
Seccomp_filters: 0
```

shell 域**根本没装 seccomp 过滤器**。在 shell 里跑探针，所有 syscall 都会返回成功，测不出任何东西。

**坑 2：`hdc shell` 不能执行任意二进制。**

```
$ hdc shell /data/local/tmp/hello_static
/bin/sh: /data/local/tmp/hello_static: Permission denied   (rc=126)
```

文件标签是 `u:object_r:data_local_tmp:s0`，shell 域是 `u:r:sh:s0`，没有 execute 权限。`chmod 777`、`chcon` 改标签、换 `/mnt` / `/dev` / `/data` 目录、`setsid` / `xargs` / `sh -c exec` / `/proc/self/fd` 各种包装、`hdc smode` 提权——**全部失败**。

对照实验：`/system/bin/base64` 原地执行 `rc=0` 成功，说明执行机制本身是好的，纯粹是 SELinux 类型限制。

### 2.2 因此改成在应用进程内直接发 syscall

写了一个最小 HAP（ArkTS + C++ NAPI），核心是内联汇编直发 `svc #0`：

```c
register long x8 __asm__("x8") = nr;   // syscall 号
register long x0 __asm__("x0") = 0;    // x0-x5 全 0
register long x1 __asm__("x1") = 0;
// ...
__asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), ...);
```

比「执行一个 ELF」好在三点：

1. 跑在自己沙箱里，绕开对 `/data/local/tmp` 的 execute 限制
2. 能拿到**真实返回值 + errno**，区分 `ENOSYS`（内核不支持）/ `EPERM`（被策略挡）/ `EFAULT`（进了内核只是参数非法）
3. 测的就是 App 进程上下文，正是我们想知道的

### 2.3 被杀进程的保护

`SECCOMP_RET_KILL` 会瞬间杀掉进程，抓不到信号。对策是**每测一项就 append + `fsync` 落盘**：

```c
FILE* f = fopen(path, "a");
fputs(item, f);
fflush(f);
fsync(fileno(f));   // 关键：不 fsync 的话进程被杀时数据还在页缓存
fclose(f);
```

进程被杀后重启，App 会读日志发现最后一条结果之后没有 `# END` 标记，就知道断在哪一项。

### 2.4 修掉一个会导致误判的坑

信号处理用了 `siglongjmp` 恢复，但初版有三个缺陷，都会让结果不可信：

| 问题 | 后果 |
|---|---|
| 结果放在**普通局部变量**里跨 `longjmp` | C 标准规定值不确定；汇编验证编译器会把结构体返回值压进 x0/x1，而 arm64 `sigsetjmp` 只保存 x19–x30 |
| 测完 `signal(SIGSEGV, SIG_DFL)` | 之后任何段错误都会崩掉整个 App，而不是被跳过 |
| 只重装 `sigaction`，没处理 pending 信号 | 已被内核标记为 pending 的同类信号会立刻重入 |

修法：结果全改 `volatile` 全局变量（强制走内存）、保存并还原**原始** `sigaction`、用 `sigprocmask` 在测试区间屏蔽这批信号、去掉 `SA_NODEFER`。

## 三、实测结果

### 3.1 纯血鸿蒙原生应用沙箱

两台设备：

| | 设备 A | 设备 B |
|---|---|---|
| 机型 | HUAWEI（云调试） | HUAWEI 手机（自有） |
| 系统 | HarmonyOS NEXT | HarmonyOS NEXT |
| 内核 | HongMeng Kernel 1.11.0 | HongMeng Kernel 1.13.0 |

进程上下文：

```
seccomp=2  filters=2  uid=2002xxxx
SELinux=u:r:debug_hap:s0:x73,x334,x512,x868,x1024
CapEff=0000000000000000  CapBnd=000000ffffffffff  NoNewPrivs=0
```

| syscall | nr | 设备 A | 设备 B |
|---|---:|---|---|
| getcwd | 17 | ✅ | ✅ |
| set_robust_list | 99 | ✅ | ✅ |
| get_robust_list | 100 | — | 💀 |
| **ptrace** | 117 | ✅ | ✅ |
| **socket** | 198 | ✅ | ✅ |
| socketpair | 199 | — | ✅ |
| accept | 202 | — | ✅ |
| connect | 203 | — | ✅ |
| **clone** | 220 | — | ✅ |
| **execve** | 221 | — | ✅ |
| mmap | 222 | — | ✅ |
| accept4 | 242 | — | ✅ |
| seccomp | 277 | — | ✅ |
| getrandom | 278 | — | ✅ |
| rseq | 293 | — | 💀 |
| io_uring_setup | 425 | — | 💀 |
| **clone3** | 435 | 💀 | 💀 |
| openat2 | 437 | — | 💀 |
| faccessat2 | 439 | — | ✅ |

「—」= 该设备上没测到这一项，不是失败。

**两个不同内核版本，关键项结果完全一致。**

### 3.2 对照组：`hdc shell`

```
u:r:sh:s0
Seccomp: 0
Seccomp_filters: 0
CapEff: 0000000000000000
CapBnd: 000000ffffffffff
NoNewPrivs: 0
```

无 seccomp 过滤器，但不能执行任意二进制。

### 3.3 对照组：安卓兼容容器

461 项中仅约 40 项放行，`socket` / `socketpair` / `accept` / `accept4` / `ptrace` / `set_robust_list` / `rseq` / `clone3` / `openat2` / `io_uring` 全部被 SIGSYS KILL。

数据来自社区此前公布的测量，本文未独立复现（只复现了故障现象）。

### 3.4 execve：能 fork，不能 exec

在应用沙箱里尝试执行一个 241 字节的静态 ELF（无 libc，只调 `write` + `exit`）：

```
目标：/data/storage/el2/base/haps/entry/files/exec/hello_static
写入：241 字节  written=1 chmod=1
fork：成功  exitCode=127
输出：EXEC_FAIL errno=13 (Permission denied)
```

- **`fork` 成功** —— 与 `clone`(220) ALLOWED 一致
- **`execve` 返回 EACCES** —— 不是文件权限问题（`chmod 0755` 成功），是 SELinux 不允许 `debug_hap:s0` 域执行这个文件

这和 `hdc shell` 里遇到的是同一类限制，只是换了域。

### 3.5 dlopen：能读能写，但不能映射为可执行

理论上 `dlopen` 走的是「文件 read + mmap」，和 `execve` 的 `execute` 权限是两回事，所以 execve 失败**不必然**意味着进程内嵌入也不行。

实际测了，而且逐步拆开看每一环：

```
目标：/data/storage/el2/base/haps/entry/files/exec/libprobelib.so
字节：1960

OK   write
OK   stat
OK   open+read          ← 能读到内容
FAIL mmap(RX) e=13      ← EACCES
FAIL dlopen             ← 数据目录里的 .so（RTLD_NOW）
FAIL dlopen             ← 数据目录里的 .so（RTLD_LAZY）
OK   dlopen             ← HAP libs/arm64/ 目录里的 .so ✅
---
❌ 不可用（仅限数据目录）
```

**断点非常明确**：`open` 和 `read` 都成功，`mmap(PROT_READ|PROT_EXEC)` 返回 EACCES。

`dlopen` 内部必须 `mmap` 代码段为可执行，这一步被拒，所以它只能报模糊的 `No error information`。

### 3.5.1 关键的对照组：HAP libs 目录可以

同一次运行里换一个位置再试：

| 位置 | dlopen | 原因 |
|---|---|---|
| 数据目录 `files/exec/` | ❌ | `mmap(PROT_EXEC)` EACCES |
| **HAP `libs/arm64/`** | ✅ **成功** | 随 HAP 一起签名，不受此限 |

这把结论从「完全不能执行外部代码」修正为精确的一句话：

> **只允许执行随 HAP 一起签名的代码。**

### 3.6 三道墙合起来看

| 操作 | 结果 | 含义 |
|---|---|---|
| `fork` / `clone` | ✅ | 能创建子进程 |
| `open` + `read` | ✅ | 能读取外部文件 |
| `execve`（自建文件） | ❌ EACCES | 不允许执行 |
| `mmap(PROT_EXEC)` | ❌ EACCES | 不允许映射为可执行 |
| `dlopen`（HAP `libs/`） | ✅ | 签名代码可以加载 |

这是典型的 **W^X + 代码签名约束**：应用沙箱只允许执行**已签名并打包进 HAP** 的代码。

**因此「进程内嵌 Node」是可行的，但前提是 Node 必须以 `.so` 形式打进 HAP 的 `libs/arm64-v8a/`，随 HAP 一起签名。** 运行时写入的 `.so` 加载不了。

### 3.7 对原生鸿蒙方案的推论

把上面合起来，原生鸿蒙应用里能跑代码的路径只剩一条：

- ❌ 启动外部二进制（execve 被拒）
- ❌ 运行时加载自己写的 .so（mmap PROT_EXEC 被拒）
- ✅ **把 Node 编译进 HAP 的 `libs/arm64-v8a/` 里，dlopen 加载**（已实测可行）

### 3.8 旁证：原生鸿蒙版已被报告可运行

2026-11-06，社区渠道出现了一段鸿蒙设备上的实机演示：冷启动约 3 秒，运行流畅。同期还有第三方贡献者报告完成了原生鸿蒙移植并提供了侧载安装包。

时间线上：

| 时间 | 事件 |
|---|---|
| 11-01 | 第三方贡献者在 issue 中提到已完成鸿蒙版本移植 |
| 11-05 13:59 | issue 维护者把分散的鸿蒙报告合并进同一个 issue |

## 四、这些数据意味着什么

### 4.1 修正一个流传较广的错误结论

> 「鸿蒙跑不了本机引擎」

需要拆成两句：

- **安卓兼容容器里**：所有关键 syscall 都被拦，本机引擎确实无解。这句成立。
- **纯血鸿蒙原生沙箱里**：`socket` / `ptrace` / `clone` / `execve` 全部可用。**这句不成立。**

### 4.2 真正的卡点是 glibc 版本

典型运行时是 Node 24.x + Ubuntu 24.04，glibc 2.39。这个组合：

- `pthread_create` 首选 `clone3`（glibc 2.34+）→ 被 KILL
- 线程初始化用 `rseq`（glibc 2.35+）→ 被 KILL
- 路径解析优先 `openat2` → 被 KILL

**所以现代 glibc 在鸿蒙原生沙箱里也起不来。** 但和容器不同，这里没有内核资源层面的封锁，纯粹是「接口不存在」——理论上可以通过换老 libc 或打运行时补丁绕过。

### 4.3 还有第三道墙：W^X

即使 glibc 问题解决，还有一道更硬的：

- **`execve` 被 SELinux 拒**（3.4）
- **`mmap(PROT_EXEC)` 被拒**（3.5）

所以「启动一个 node 进程」和「运行时加载自己的 .so」两条路都堵死。唯一剩下的是：**把 Node 编译进 HAP 的 `libs/arm64-v8a/`，由系统加载器加载**——这类代码随 HAP 一起签名，不受这条限制。

## 五、复现

### 5.1 目录结构

```
harmony-syscall-probe/
├─ docs/
│  └─ 鸿蒙沙箱能力实测.md        本文
├─ hap/SysProbe/                应用沙箱探针（ArkTS + C++ NAPI）
│  └─ entry/src/main/
│     ├─ cpp/
│     │  ├─ sysprobe.cpp        内联汇编 svc #0 + 信号保护 + fsync 落盘
│     │  ├─ execprobe.cpp       fork + execve 测试
│     │  ├─ dlprobe.cpp         dlopen 逐步诊断
│     │  ├─ probelib.c          被 dlopen 的最小库（无动态依赖）
│     │  └─ CMakeLists.txt
│     └─ ets/pages/Index.ets    界面
└─ tools/
   ├─ gen_probes.py             生成单 syscall 静态 ELF（容器环境用）
   ├─ run_probes.py             经 hdc 推送执行（容器环境用）
   └─ gen_static_elf.py         生成 hello / socket_probe 两个静态 ELF
```

### 5.2 构建 HAP

```powershell
$env:DEVECO_SDK_HOME = "D:\DevEco Studio\sdk"
$env:PATH = "D:\DevEco Studio\tools\node;D:\DevEco Studio\tools\ohpm\bin;$env:PATH"
$env:NODE_HOME = "D:\DevEco Studio\tools\node"
cd hap\SysProbe
node "D:\DevEco Studio\tools\hvigor\bin\hvigorw.js" --mode module `
  -p product=default -p module=entry@default assembleHap --no-daemon
```

签名：在 `build-profile.json5` 的 `signingConfigs.material` 里填自己的证书路径，
或在 DevEco Studio → Project Structure → Signing Configs 里点自动生成。

### 5.3 使用

装好后打开 App，界面里有：

- **19 个方块**：点一个测一项。进程被杀后重启，那个方块会变红底。
- **「跑剩余关键项」/「跑全量 462」**：批量跑，自动跳过已知会杀进程的项。
- **「exec hello」/「exec socket」**：测 fork+execve。
- **「dlopen .so」**：逐步诊断 dlopen。
- **「复制报告」**：导出 Markdown。

### 5.4 容器环境（LD_PRELOAD 式探针）

```powershell
python tools\gen_probes.py --critical     # 生成 19 个关键探针
python tools\run_probes.py --critical     # 经 hdc 推送执行
```

## 六、局限

1. 只测了 19 个关键项，不是全量 462 项。
2. 云调试那台设备只测了 4 项，不是完整对照组。
3. 测的是 `debug_hap:s0` 域。**正式签名应用的域可能不同**，未验证。
4. 「💀」是通过「点下一项时 App 已消失」判定的，没有拿到具体信号编号（`SECCOMP_RET_KILL` 不投递信号）。
5. 安卓兼容容器的数据引用社区此前公布的测量，本文未独立复现。
6. 3.8 的鸿蒙实机演示是社区渠道消息，不是正式发布，也未经本文独立验证。
